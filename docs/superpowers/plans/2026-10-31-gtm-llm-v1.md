# PushPress GTM LLM v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A PushPress rep can ask qm a GTM question and get a cited draft from the Onyx Notion brain, with Informatics visible only to the four named viewers.

**Architecture:** One plan covers both systems. A rep gets an answer only when qm and Onyx are both up, and staging runs the same software as prod. Onyx Community Edition on its own VM is the brain. qm 0.1.15 on Fly is the front door. qm calls one Onyx MCP server with that rep's personal access token. A Cloudflare Worker adds the Access service token on `/mcp` because qm's per-user MCP client does not send extra headers.

**Tech Stack:** Onyx Community Edition (MIT, Docker Compose), qm 0.1.15 (`@yc-software/qm`), Fly.io, Fly Sprites, Supabase Postgres, Google OIDC, OpenAI, Cloudflare DNS, Cloudflare Access, a Cloudflare Worker, Slack Socket Mode, Sentry.

**Spec:** `gtm/README.md`, `gtm/UPSTREAM_CHANGES.md`, `gtm/config/gtm.yaml`, `gtm/qm/INTEGRATION.md`, `gtm/qm/layer/`, `gtm/evals/`, and `.env.gtm.example`. qm field names also come from yc-software/qm commit `f357718980410ae72147f48529154da3a73a38cf` (CLI 0.1.6). `https://github.com/GTM-RevOps/qm-deploy` was not readable here on 2026-10-31.
